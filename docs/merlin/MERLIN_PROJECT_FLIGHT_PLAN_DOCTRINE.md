# MERLIN PROJECT FLIGHT PLAN DOCTRINE

## Core Principle

Merlin App Builder exists to help builders go from idea to product, launch, growth, and scale without headache, drift, missed steps, or context loss.

The system must help people do what experienced builders do manually: hold the vision, track the evidence, sequence the work, prevent drift, validate progress, and keep moving toward measurable outcomes.

## Required Artifact

Every Merlin App Builder project must generate a Project Flight Plan before Codex execution.

The Project Flight Plan is the anti-drift operating map for the project.

It must define the entire path from idea to users, revenue, growth, and scale.

## Required Project Flight Plan Sections

Every Project Flight Plan must include:

1. Destination
2. Current State
3. Required Assets
4. Missing Assets
5. Roadblocks
6. Build Phases
7. Growth Phases
8. KPIs
9. Decision Gates
10. Codex Task Queue
11. Council Review Points
12. Launch Checklist
13. Scale Checklist
14. Revert / Disable Strategy

## Canonical Project Journey

The Project Flight Plan must guide projects through:


## Destination

The Destination section must define:

- What the project becomes
- Who it serves
- What problem it solves
- What success means
- What milestone proves arrival

For scale projects, the destination must include the path toward major adoption, including the long-term ambition of reaching millions of users when appropriate.

## Current State

The Current State section must define:

- Existing assets
- Existing repositories
- Existing product state
- Existing users
- Existing constraints
- Current blockers
- Current evidence quality

## Required Assets

The Required Assets section must define what the project needs to progress.

Examples:

- Domain
- Repository
- Brand assets
- Product doctrine
- User research
- Data model
- App shell
- Admin tools
- Analytics
- Launch page
- Support workflow
- Legal/privacy requirements

## Missing Assets

The Missing Assets section must identify what is absent, incomplete, stale, or unverified.

Merlin must not pretend missing assets exist.

Missing assets must become tasks, blockers, or explicit assumptions.

## Roadblocks

The Roadblocks section must identify:

- Technical risks
- Market risks
- UX risks
- Data risks
- Trust risks
- Legal/compliance risks
- Distribution risks
- Revenue risks
- Team/operations risks

## Build Phases

The Build Phases section must sequence work from doctrine to production readiness.

Minimum phases:

1. Doctrine and evidence baseline
2. MVP architecture
3. Core data model
4. Core user flow
5. Admin/review layer
6. Validation and tests
7. Launch surface
8. Analytics and KPI capture
9. Onboarding
10. Monetization when appropriate

## Growth Phases

The Growth Phases section must sequence growth from first users to scale.

Minimum phases:

1. First 10 users
2. First 100 users
3. First 1,000 users
4. First 10,000 users
5. First 100,000 users
6. First 1,000,000 users

Each phase must define the main acquisition channel, activation goal, retention signal, and risk gate.

## KPIs

Every Project Flight Plan must define measurable KPIs.

KPIs must include:

- Activation metric
- Retention metric
- Conversion metric
- Quality metric
- Growth metric
- Revenue metric when applicable

Merlin must connect every major build slice to at least one KPI or doctrine requirement.

## Decision Gates

Decision Gates are required before major changes.

Minimum gates:

- Doctrine approved
- Market proof sufficient for MVP
- MVP scope approved
- Architecture approved
- First slice approved
- Launch readiness approved
- Growth loop approved
- Monetization approved when applicable
- Scale readiness approved

Human authority is final at all decision gates.

## Codex Task Queue

The Codex Task Queue must break execution into small approved slices.

Each task must include:

- Slice ID
- Goal
- Doctrine reference
- Flight Plan reference
- Files to inspect
- Required changes
- Forbidden changes
- Acceptance criteria
- Validation commands
- Feature flag or config gate when applicable
- Enable instructions
- Disable instructions
- Revert instructions
- Safe-disable behavior
- User impact if disabled
- Validation after revert
- Rollback risk
- Expected user-visible outcome

Codex is execution only.

Codex may not self-authorize work.

## Council Review Points

The Albion Council is the governance review layer for Merlin App Builder.

Council review is required at major gates.

Council may:

- Review proposals
- Challenge assumptions
- Identify risk
- Recommend next steps
- Request more evidence
- Evaluate tradeoffs

Council may not:

- Self-authorize execution
- Override human authority
- Rewrite doctrine without approval
- Treat model opinion as evidence

## Launch Checklist

Every Project Flight Plan must include a launch checklist.

Minimum launch checklist:

- Core flow tested
- Error states tested
- Auth/permissions tested when applicable
- Analytics/KPIs active
- Support path available
- Public copy reviewed
- Admin/review path available when needed
- Rollback plan defined
- Rollback/disable route documented
- Migration rollback requirements reviewed when applicable
- Deployment rollback requirements reviewed when applicable
- Validation after revert
- Launch decision approved

## Scale Checklist

Every Project Flight Plan must include a scale checklist.

Minimum scale checklist:

- Infrastructure risk reviewed
- Database growth reviewed
- Cost model reviewed
- Support model reviewed
- Trust and safety reviewed
- Security posture reviewed
- Growth channel dependency reviewed
- Revenue model reviewed when applicable
- Team/operations requirements reviewed

## Model-Agnostic Requirement

Users may plug in their own AI models.

User-connected models may assist with drafting, research, planning, coding support, or review.

They do not own Merlin governance.

Merlin owns:

- Intake
- Memory
- Evidence
- Routing
- Truth Logic
- Validation
- Audit history
- Project state

Albion Council owns governance review.

Human authority remains final.

Changing models must never alter memory, evidence, decisions, governance records, audit history, or project state.

## Anti-Drift Rule

If a project action does not map to doctrine, a Flight Plan section, a KPI, a decision gate, or an approved Codex task, it must be treated as drift until reviewed.

Merlin must surface drift early instead of allowing the project to wander.

## Final Outcome

The Project Flight Plan exists to make ambitious builders more consistent.

The target is not just app creation.

The target is durable execution from idea to millions of users.
