# MERLIN APP BUILDER PLAN

## Core Definition

Merlin App Builder is part of Merlin OS Action Layer.

It is not a generic prompt-to-app generator.

It is a guided execution system for builders who need to move from idea to product, launch, growth, and scale without headache, project drift, missed steps, or context loss.

Merlin App Builder exists to help people build the way experienced operators build: with structure, memory, evidence, priorities, checkpoints, and execution discipline.

## Primary Mission

Merlin App Builder turns messy human intent into a durable project operating map and executable build path.

The canonical flow is:

```text
Idea
↓
Evidence
↓
Route
↓
Doctrine
↓
Plan
↓
Slice
↓
Codex
↓
PR
↓
Validation
↓
Launch
↓
Growth
↓
Scale
```

The goal is not app generation alone.

The goal is durable execution from idea to millions of users.

## Required System Layers

### 1. Merlin Intake

Merlin Intake accepts messy input:

- Voice notes
- Screenshots
- Documents
- Spreadsheets
- Existing repositories
- Chat instructions
- Competitor examples
- Business rules
- Brand notes
- User workflows

Merlin Intake produces:

- Project Brief
- Evidence Registry
- Known Constraints
- Unknowns
- Initial App Type
- Risk Flags

### 2. Route Logic Engine

Every project is routed like navigation.

The route must define:

- Destination
- Current State
- Available Resources
- Roadblocks
- Required Checkpoints
- Next Best Slice
- Arrival Proof

Merlin must not jump directly from idea to code.

### 3. Truth Logic Engine

Truth Logic handles conflicting inputs, incomplete information, and evidence gaps.

When inputs conflict, Merlin must produce:

- Conflict
- Evidence A
- Evidence B
- Confidence
- Resolution Needed
- Safe Next Step

Merlin must not replace evidence with model opinion.

### 4. Doctrine Generator

Every project must have doctrine before implementation begins.

Doctrine must define:

- What the product is
- What the product is not
- User types
- Authority model
- Data rules
- Monetization rules
- Safety rules
- UX principles
- Forbidden behavior
- KPI targets

Doctrine exists to protect the project from drift.

### 5. Albion Council Governance

The Albion Council is Merlin's governance layer.

The Council reviews:

- Product logic
- Risk
- Missing evidence
- Architecture
- Monetization
- UX clarity
- Validation plan
- Scale readiness

The Council may advise, challenge, or recommend.

The Council may not self-authorize execution.

Human authority is final.

### 6. Architecture Generator

Merlin App Builder produces a complete technical outline before Codex execution.

The architecture must define:

- Frontend surfaces
- Backend services
- Database schema
- API contracts
- Authentication and authorization
- State model
- Event tracking
- Deployment target
- Test plan
- Monitoring needs

### 7. Slice Planner

Merlin App Builder breaks work into small executable slices.

Each slice must include:

- Goal
- Files likely affected
- Acceptance criteria
- Validation commands
- Rollback risk
- Codex prompt
- Expected user-visible outcome

No build should begin as a giant unsliced task.

### 8. Codex Handoff

Codex is execution only.

Codex receives complete task packets from Merlin.

A Codex handoff must include:

- Repository
- Branch
- Doctrine
- Slice
- Files to inspect
- Required changes
- Forbidden changes
- Validation commands
- Expected output
- Commit message
- PR summary

Codex does not own final authority.

## Model-Agnostic Rule

Users may plug in their own AI models.

Supported model categories include:

- OpenAI
- Anthropic
- Google Gemini
- xAI
- Local/self-hosted models
- Future providers

User-connected models may generate, draft, research, or assist.

User-connected models do not own governance, memory, evidence, routing, validation, audit history, or project state.

Model swaps must not alter:

- Memory
- Evidence
- Decisions
- Governance records
- Audit history
- Project state

## Project Flight Plan Requirement

Every project must generate a Project Flight Plan before Codex execution.

The Project Flight Plan is the anti-drift artifact.

It maps the entire journey from idea to product, launch, growth, and scale.

## Required Output Per Project

Every Merlin App Builder project must produce:

1. Vision Outline
2. Doctrine Outline
3. Market Outline
4. Product Outline
5. Technical Outline
6. Build Slice Outline
7. Launch Outline
8. Growth Outline
9. Scale Outline
10. Project Flight Plan
11. Codex Task Queue
12. Council Review Points
13. Validation Gates

## Strategic Position

Merlin App Builder competes on:

- Better execution structure
- Better continuity
- Better project memory
- Better validation
- Better decision gates
- Better handoffs to coding agents
- Lower operator headache

It does not compete by claiming to own the best foundation model.

Merlin becomes more valuable as external models improve.
