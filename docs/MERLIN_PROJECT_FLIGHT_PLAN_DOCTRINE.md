# Merlin Project Flight Plan Doctrine

## Core principle

Merlin App Builder exists to help builders move from idea to product, launch, growth, and scale without headache, drift, missed steps, or context loss.

The goal is not app generation alone.

The goal is durable execution from idea to millions of users.

## Required flow

Every Merlin App Builder project must follow this operating path:

Idea
-> Doctrine
-> Market Proof
-> MVP Scope
-> Build Plan
-> Repo Setup
-> Slices
-> Codex Execution
-> Testing
-> Launch
-> User Acquisition
-> Metrics
-> Iteration
-> Scale

Merlin must not jump directly from idea to code.

Merlin must create the project operating map before implementation starts.

## Project Flight Plan requirement

Every project must generate a Project Flight Plan before Codex execution.

The Project Flight Plan is the anti-drift artifact.

It exists to keep the project aligned, sequenced, measurable, and reviewable from start to finish.

## Required Project Flight Plan sections

Every Project Flight Plan must include:

1. Destination
2. Current State
3. Required Assets
4. Missing Assets
5. Roadblocks
6. Build Phases
7. Growth Phases
8. KPIs
9. Decision Gates
10. Codex Task Queue
11. Council Review Points
12. Launch Checklist
13. Scale Checklist

## 1. Destination

The Destination defines the end state.

It must answer:

- What are we building?
- Who is it for?
- What pain does it remove?
- What outcome does the product create?
- What does success look like at MVP, launch, and scale?

The Destination must be specific enough to guide execution.

## 2. Current State

The Current State defines the project starting point.

It must include:

- Existing idea notes
- Existing code or repositories
- Existing assets
- Existing users or customers
- Existing traction
- Existing gaps
- Existing constraints

Merlin must separate what exists from what is assumed.

## 3. Required Assets

Required Assets are the materials needed to execute the project.

They may include:

- Brand assets
- Domain names
- Repositories
- Database access
- API keys
- User research
- Competitive evidence
- Product screenshots
- Legal/compliance notes
- Launch copy
- Analytics tools
- Deployment targets

Merlin must identify missing required assets before execution.

## 4. Missing Assets

Missing Assets must be listed explicitly.

Each missing asset must include:

- Why it matters
- Whether execution is blocked
- Safe fallback if unavailable
- Owner responsible for providing it

Merlin must not silently proceed when a missing asset creates risk.

## 5. Roadblocks

Roadblocks are anything likely to slow, block, or distort execution.

Roadblocks may include:

- Technical unknowns
- Legal risk
- Market uncertainty
- Weak onboarding
- Missing data
- Bad UX
- Unclear monetization
- Infrastructure limits
- Security risk
- Founder availability
- Model limitations
- API cost exposure

Each roadblock must include a mitigation plan.

## 6. Build phases

Build Phases define the staged path from concept to usable product.

Required phases:

1. Doctrine and baseline
2. Product architecture
3. Core data model
4. First user flow
5. Admin/review layer
6. Validation and tests
7. Public launch surface
8. Analytics and KPIs
9. Onboarding
10. Monetization, if needed
11. Growth loops
12. Scale hardening

Each phase must be broken into executable slices.

## 7. Growth phases

Growth Phases define how the product moves from first users to large-scale adoption.

Required growth checkpoints:

1. First 10 users
2. First 100 users
3. First 1,000 users
4. First 10,000 users
5. First 100,000 users
6. First 1,000,000 users

Each checkpoint must include:

- Acquisition channel
- Activation goal
- Retention signal
- Conversion metric
- Feedback loop
- Operational risk
- Next scale constraint

## 8. KPIs

Every project must have measurable KPIs.

Required KPI categories:

- Acquisition
- Activation
- Retention
- Revenue, if applicable
- Referral or virality, if applicable
- Reliability
- Support burden
- User trust
- Completion rate
- Time-to-value

Merlin must connect each build slice to at least one KPI or explain why the slice is foundational.

## 9. Decision Gates

Decision Gates prevent drift and premature execution.

Required gates:

1. Doctrine approved
2. Market proof reviewed
3. MVP scope approved
4. Technical architecture approved
5. First build slice approved
6. Validation passed
7. Launch readiness approved
8. Growth readiness approved
9. Scale readiness approved

Codex execution must not begin before the relevant gate is approved.

## 10. Codex Task Queue

The Codex Task Queue converts the Flight Plan into executable work.

Each Codex task must include:

- Task name
- Slice ID
- Goal
- Repo
- Branch
- Context summary
- Files to inspect
- Required changes
- Forbidden changes
- Acceptance criteria
- Validation commands
- Rollback risk
- Expected output
- Commit message
- PR summary

Codex is execution only.

Codex does not own authority.

## 11. Council Review Points

Albion Council review is required at major gates.

Council review points must include:

- Doctrine review
- Market logic review
- MVP scope review
- Architecture review
- Risk review
- Launch readiness review
- Scale readiness review

The Council may advise, challenge, or recommend.

The Council may not self-authorize.

Human authority is final.

## 12. Launch checklist

Every project must include a Launch Checklist.

Required launch items:

- Production environment ready
- Public landing surface ready
- Core user flow tested
- Analytics installed
- Error monitoring active
- Support path defined
- Feedback capture active
- Privacy/security reviewed
- Smoke tests passed
- Rollback path defined
- First-user acquisition plan ready

A project is not launch-ready until the checklist is complete or exceptions are explicitly approved.

## 13. Scale checklist

Every project must include a Scale Checklist.

Required scale items:

- Database scalability reviewed
- Infrastructure cost reviewed
- Support burden reviewed
- Abuse and trust risks reviewed
- Onboarding bottlenecks reviewed
- Retention data reviewed
- Revenue model reviewed
- Operational ownership defined
- Monitoring coverage reviewed
- Incident response path defined

Scaling must be based on evidence, not optimism.

## Merlin responsibilities

Merlin owns:

- Intake
- Memory
- Evidence
- Routing
- Truth logic
- Project state
- Validation gates
- Audit history
- Codex handoff preparation
- Flight Plan continuity

Merlin must preserve project continuity across sessions, files, models, and repos.

## User model boundary

Users may plug in their own AI models.

User-connected models may assist with:

- Brainstorming
- Drafting
- Research
- Coding support
- Alternative analysis
- Review

User-connected models do not own:

- Governance
- Project state
- Evidence history
- Audit history
- Human authority
- Council authority
- Final approval

Model swaps must not alter memory, evidence, decisions, governance records, audit history, or project state.

## Codex boundary

Codex is the execution engine.

Codex may:

- Inspect code
- Modify files
- Add tests
- Run validation
- Fix failures within scope
- Prepare commits
- Prepare PR summaries

Codex may not:

- Skip doctrine
- Skip the Flight Plan
- Broaden scope without approval
- Override human authority
- Self-authorize execution
- Treat model output as evidence
- Rewrite governance history

## Human authority

Human authority is final.

AI may advise.

AI may challenge.

AI may validate.

AI may execute approved tasks.

AI may not override the human decision-maker.

## Anti-drift rule

If a requested action conflicts with the Project Flight Plan, doctrine, evidence, or approved slice scope, Merlin must stop and surface the conflict.

Merlin must then produce:

- The conflict
- The evidence
- The risk
- The safest next step
- The approval required to proceed

## Strategic position

Merlin App Builder does not compete as another prompt-to-app generator.

Merlin App Builder competes as a full execution operating system for builders.

It helps users move from idea to millions of users by enforcing:

- Structure
- Memory
- Evidence
- Sequencing
- Governance
- Validation
- Accountability
- Repeatable execution

The product promise is simple:

Less drift.
Fewer missed steps.
Better execution.
Cleaner handoff.
Higher chance of reaching scale.
